## EditableMesh batch APIs, timed (research)

Allen asked whether Roblox's new EditableMesh batching and parallel queries (DevForum, "Full Release: EditableMesh Batching APIs & Parallel Queries") would help, then "Yes, time it". Timed in Edit (Studio 0.745) against a cloned `Shared`. **No game code changed.**

- **The APIs work here:** `BatchAdd` (Vertex, Color with alphas, Face as `{{v1, v2, v3}}`), `BatchSetFaceAttributes(faceIds, {{c1, c2, c3}})` and `BatchSetValues(ids, values)` all ran. Batched vertex positions matched `BladeView:setParams` exactly (max error 0).
- **Medians, 782-vertex blades (tantō, katana, longsword, zanbato all about the same):**

| Call | Now (per-element loop) | Batched |
| --- | --- | --- |
| `BladeView:setParams` (each frame of a strike's deform tween, each grind step) | 0.27–0.32 ms | 0.16–0.18 ms |
| `BladeView:setFinish` | 0.34–0.40 ms | 0.19–0.23 ms |
| Filling the mesh in `BladeView.new` (katana) | 1.63 ms | 0.75 ms |
| `CreateMeshPartAsync` in `BladeView.new` | 13.85 ms | unchanged |
| Whole `BladeView.new` | about 16 ms | about 16.5 ms (no gain) |

- **What it means:** batching saves about 0.1–0.2 ms per frame while the anvil or polishing blade is changing, under 1% of a 16 ms frame on PC. A phone might gain a few times that. Building a blade is held up by `CreateMeshPartAsync`, which batching doesn't touch. Parallel queries would only speed up `BladeView:raycast`, which runs once per grind input. The big hitches are still etching (EditableImage), which this update leaves alone.
- **Claude's call:** not worth changing `BladeView` for now. Revisit if a phone profile shows `setParams` in the deform tween.

## Etch build hitch fixed

Allen said yes to looking at the etching hitches next. Timed in Edit against a cloned `Shared`, then changed `Shared.EtchCanvas`. **Not played.**

- **Where an etch build's time goes (Edit, PC), tantō / katana:** blank image 35–80 / 107–134 ms (only the first time per body colour and layout), strokes drawn 24–68 / 71–449 ms, the final paint (`_flush`) 6–16 / 18–79 ms, bake 0–25 ms (one frame, measured on new images). WovenWind is the heaviest pattern.
- **The hitch:** a spread build (`SwordMeshCache.etch(..., spread = true)`: `SwordRenderer`, the Polishing Station) spread the blank paint and the pieces over frames, but `_flush` then painted every raised pixel in one frame: up to 80 ms on a katana. That was the 58 ms frame in [[Development/Technical Debt and Deferred Features]].
- **The fix:** `reveal` passes `spread` to `_flush`, which yields every 4 ms (`SLICE`) while painting, and stops if the canvas is destroyed while it waits. Unspread reveals (the show's frame-by-frame drawing, the spec) are unchanged.
- **Worst frame of a whole spread build (Edit, Heartbeat gaps):** katana Eclipse 52 → 23 ms, katana Fracture 64 → 21 ms, tantō Tide 26 → 21 ms, katana WovenWind 84 → 21 ms on repeat builds. The first build after a fresh module load still had one 73–78 ms frame (only on the first run of each test: likely a warm-up or garbage collection, not one etch step).
- **Checks (Edit):** `EtchingSpec` 45 pass, 8 fail; the same 8 fail with the old `_flush` call swapped back in (each blade's "tool surface on the real blade", gap about 0.24 studs, and "two Eclipse materials share one overlay mesh"), so they predate this. Spread == unspread canvas checks pass.
- **Not done:** the 8 old `EtchingSpec` failures.
- **To test in Play:** open the Etching Table's pattern picker on a katana and watch for a freeze; rack an etched katana and polish an etched one across a sheen level.
